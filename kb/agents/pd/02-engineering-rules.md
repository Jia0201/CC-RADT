# PD 工程规则

## 需求事实

- 什么时候使用：用户口述、issue、会议纪要或历史上下文中同时包含事实、猜测和愿望时。
- Codex 生成内容时要遵守：区分已确认事实、合理推断和待确认问题；不能把推断写成确定需求。

## 产品目标

- 什么时候使用：需求需要说明为什么做、成功后改变什么、如何判断完成时。
- Codex 生成内容时要遵守：目标必须能连接用户价值或业务结果；避免只写“优化”“完善”“支持”等空泛目标。

## 用户与场景

- 什么时候使用：涉及多角色、权限、使用路径、前后台、运营或管理端时。
- Codex 生成内容时要遵守：写清角色、触发条件、主路径、异常路径和可观察结果；不把内部模块名当作用户场景。

## 范围与非目标

- 什么时候使用：需求容易蔓延、存在多个版本、多个平台或多个可选能力时。
- Codex 生成内容时要遵守：明确本次范围、非目标、未来可能项和边界原因；不得用模糊范围给下游制造隐性承诺。

## 验收标准

- 什么时候使用：需求需要交给 Plan-PM、QA 或 Dev 拆解前。
- Codex 生成内容时要遵守：验收标准必须可观察、可测试、可判断通过或失败；每条标准对应具体行为、数据或状态。

## 兼容与迁移

- 什么时候使用：需求影响既有用户、数据、API、权限、配置、文档或工作流时。
- Codex 生成内容时要遵守：写清向后兼容、数据迁移、灰度、回滚和用户告知需求；不把兼容风险留给实现阶段猜测。

## 风险与待确认

- 什么时候使用：信息不足、约束冲突、业务规则不完整或验收边界不稳定时。
- Codex 生成内容时要遵守：风险说明影响面和触发条件；待确认问题必须具体到可回答的问题。

## 下游交接

- 什么时候使用：需求需要进入计划、研发、测试、文档或安全审查时。
- Codex 生成内容时要遵守：交接内容包含目标、范围、关键规则、验收、风险和开放问题；不写调度动作或命令式派工。
