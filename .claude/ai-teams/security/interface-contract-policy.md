# 接口契约治理规则

本规则用于治理前端、后端、QA 和 Doc 共同依赖的接口契约。接口实现、Mock、测试和文档必须引用同一份已登记契约，禁止仅依赖口头约定、聊天记录或单端实现推断字段。

## 1. 适用范围

以下变化必须建立或更新接口契约：

- HTTP、RPC、GraphQL、WebSocket、消息事件和跨模块公共接口。
- 请求参数、响应字段、错误模型、鉴权、分页、排序、过滤、幂等和限流行为。
- 前端消费的枚举、状态机、时间、金额、精度、文件地址和可空字段。
- Mock、SDK、类型定义、Schema 或测试夹具与真实接口之间的映射。

纯内部且不跨模块的私有函数不强制建立独立契约；一旦被多个模块、Agent 或客户端消费，即进入本规则范围。

## 2. 单一事实源

1. 正式契约放在 `shared/contracts/`，入口为 [index](../shared/contracts/index.md)。
2. 新契约使用 [API_CONTRACT_TEMPLATE](../shared/contracts/API_CONTRACT_TEMPLATE.md)；契约文件名应稳定、可识别，并在索引登记 Owner、状态和版本。
3. OpenAPI、GraphQL Schema、Protobuf、JSON Schema 或强类型定义可作为机器可读事实源，但必须从契约文档双向链接，说明生成方向和权威优先级。
4. 实现、Mock、测试、SDK 与文档冲突时，不得静默选择一方；应暂停合并，由接口 Owner 明确修订契约或实现。
5. `draft` 契约可用于讨论和并行开发；只有 `approved` 契约可作为发布和 QA 放行依据。

## 3. 契约建立与冻结

接口 Owner 通常由后端实现负责人承担；涉及多服务或公共平台时由 Lead 明确指定。前端负责人是消费方确认人，QA 是可验证性确认人，Doc 是文档完整性确认人。

进入并行开发前，至少冻结以下内容：

1. 接口标识、协议、路径或主题、方法和版本。
2. 鉴权方式、权限范围、幂等规则、超时和重试语义。
3. 请求字段和响应字段，包括类型、必填性、可空性、默认值、格式、单位、约束和示例。
4. 成功状态、业务状态、错误码、错误结构和可重试性。
5. 分页、排序、过滤、时间与时区、金额与精度、ID 表达方式。
6. 兼容策略、弃用时间表、Mock/Schema 位置和 QA 验收项。

任一必需项未确定时，契约保持 `draft`，不得宣称已冻结。

## 4. 前后端字段契约

每个跨端字段必须在契约表中逐项声明，禁止用“同模型”“按后端返回”或“前端自行处理”代替字段定义。

| 维度 | 强制规则 |
|---|---|
| 字段名 | 明确传输名及命名风格；重命名视为契约变更 |
| 类型 | 使用协议可表达的精确类型；禁止以 `any`、`object` 代替稳定结构 |
| 必填与可空 | `required` 与 `nullable` 分开声明；缺失、`null`、空字符串、空数组的语义不得混同 |
| 默认值 | 明确由服务端填充、客户端填充或无默认值；不得两端各自猜测 |
| 枚举 | 列出当前值、未知值处理和新增枚举值的兼容策略 |
| 数字 | 声明整数/小数、范围、单位和精度；金额优先使用最小货币单位整数或明确的小数字符串 |
| ID | 声明字符串或整数；超出 JavaScript 安全整数范围的 ID 必须使用字符串传输 |
| 时间 | 声明格式、时区和精度；默认使用含时区的 ISO 8601，禁止无说明的本地时间 |
| 布尔值 | 仅使用协议布尔值；禁止用 `0/1`、`yes/no` 混代表达，除非契约明确 |
| 嵌套对象 | 定义完整子字段；说明对象本身及子字段的可空性 |
| 数组 | 定义元素类型、顺序语义、去重规则、空数组与缺失的差异 |
| 文件/URL | 声明 MIME、大小、有效期、访问权限和 URL 是否可持久化 |
| 展示映射 | 后端字段与前端 ViewModel 不一致时，记录映射位置、生成规则和负责人 |

前端不得把未声明字段作为稳定依赖；后端不得在无兼容评估时删除字段、改变类型、改变可空性或复用既有字段表达新语义。

## 5. 响应与错误契约

1. 成功响应必须明确 HTTP/协议状态、业务状态和数据载荷结构。
2. 错误响应必须具有稳定的机器可读错误码；错误码、展示消息、调试详情和追踪 ID 应分离。
3. 契约必须列出认证失败、授权失败、参数错误、资源不存在、冲突、限流、依赖失败和服务端异常中适用的情形。
4. 每个错误声明触发条件、协议状态、客户端动作、是否可重试和是否需要上报。
5. 禁止前端仅解析自然语言错误消息驱动业务分支。

## 6. 变更与兼容性

### 6.1 非破坏性变更

- 新增可选字段，且旧客户端忽略未知字段时。
- 新增端点或独立能力，不改变既有行为时。
- 扩充文档、示例或约束说明，且不改变运行语义时。

新增枚举值、收紧校验、改变默认值或排序即使不改字段类型，也必须按消费方能力评估，不能自动视为非破坏性。

### 6.2 破坏性变更

删除或重命名字段、改变类型/单位/格式、必填性或可空性收紧、错误码语义变化、鉴权变化、分页语义变化以及行为含义变化，均属于破坏性变更。

破坏性变更必须：

1. 提升主版本或提供新端点/新主题。
2. 记录受影响消费方、迁移步骤、双轨期、弃用日期和回滚方案。
3. 获得接口 Owner、前端消费方、QA 和 Lead 明确确认。
4. 由 Doc 同步契约、索引、项目文档和相关 标准 Markdown 链接。

## 7. 变更流程

1. **提出**：变更方基于模板更新契约，标注变更摘要和兼容性分类。
2. **评审**：接口 Owner 校验服务端语义，消费方校验字段可用性，QA 校验可测试性，Security-Reviewer 校验鉴权与敏感数据边界。
3. **批准**：确认人和日期写入契约，状态改为 `approved`。
4. **实现**：前后端、Mock、Schema、SDK 和测试引用同一契约版本。
5. **验证**：执行第 8 节 QA 门禁，并把证据链接写回契约。
6. **发布**：确认兼容期、监控、弃用和回滚条件后发布。
7. **归档**：被替代版本保留历史状态并指向新版本，不直接删除。

紧急修复不得跳过契约补录。无法事前更新时，必须在同一修复任务关闭前补齐契约、QA 证据和 Doc 更新结论。

## 8. QA 门禁

接口进入 `approved`、合并或发布前，QA 必须确认：

- 契约完整性：所有请求、响应和错误字段均有类型、必填性、可空性、约束和示例。
- Schema/类型一致性：机器可读 Schema、前端类型、后端 DTO/模型与契约无已知漂移。
- 正常路径：至少覆盖一个契约示例和真实集成路径。
- 边界路径：覆盖缺失、`null`、空值、上下界、未知枚举、超长文本、精度和时区。
- 错误路径：校验协议状态、错误码、客户端动作、重试和追踪信息。
- 兼容性：旧客户端/旧服务端组合在声明的兼容窗口内通过，或已有明确阻断与迁移记录。
- 安全性：鉴权、越权、敏感字段暴露、日志脱敏、文件访问和输入校验符合要求。
- 证据：自动化测试、契约测试、集成测试或人工验证结果已链接到契约。

以下任一情况必须阻断：使用未批准契约发布；字段定义缺失或前后端理解不一致；破坏性变更无版本/迁移方案；关键错误路径未定义；QA 证据缺失且无 Lead 批准的例外。

## 9. Doc 更新职责

Doc 负责维护契约文档网络，不替代接口 Owner 决定业务语义。

Doc 必须：

1. 在 [index](../shared/contracts/index.md) 登记契约、Owner、消费方、状态、版本和最后更新时间。
2. 检查契约文件 frontmatter、标准 Markdown 链接、相关项目文档和机器可读 Schema 链接。
3. 在契约获批、变更、弃用、替代或归档时同步索引，并保留历史指向。
4. 汇总 QA 证据、已知差异、迁移窗口和未关闭风险，不把未验证推测写成事实。
5. 任务关闭前向 Lead 给出“已更新 / 无需更新 / 待确认 / blocked”结论。

接口 Owner 负责及时提供字段语义和服务端行为；前端负责人负责提供消费映射和兼容结论；QA 负责提供验证事实；Security-Reviewer 负责规则、鉴权和敏感数据边界。任何一方发现实现与契约漂移，都必须发起修订，不得等待 Doc 自行推断。

## 10. 例外与升级

例外必须记录原因、范围、风险、批准人、到期日期和补救任务。例外不改变本规则本体，也不得永久替代字段契约。出现争议、无法兼容、涉及敏感数据或无法形成可测试契约时，按 [escalation-policy](./escalation-policy.md) 回流给 Lead 和 Security-Reviewer。
