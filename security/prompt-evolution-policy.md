# 提示词自进化与受控激活规则

提示词自进化是“失败证据 -> 根因路由 -> 候选变更 -> 回归评测 -> 多方评审 -> 受控激活 -> 监控与回滚”的闭环。它不允许 Agent 在失败后直接修改自己的 active 提示词。

## 1. 触发信号

以下信号可以创建 Prompt Evolution 事件：

- Agent 输出不符合目标、范围、验证或交接契约。
- Lead 选错 Agent、任务下发缺少必要变量或上下文。
- QA 发现稳定复现的提示词缺陷。
- Security-Reviewer 发现注入、越权、敏感内容或权限扩张风险。
- 用户明确纠正 Agent 行为、职责、字段、遗漏或调度方式。
- 同类失败重复发生。
- Lead 接管、定向重试或回流证明现有提示词无法稳定执行。
- Hook 捕获 `PostToolUseFailure`、`PermissionDenied`、`SubagentStop`、`TaskCompleted`、`StopFailure` 等结构化信号。

Hook 只负责采集、脱敏和写入事件，不得判断最终根因，不得生成候选，不得编辑或激活提示词。

## 2. 根因先于改词

Lead 与 QA 必须先判断问题属于哪里：

| 根因 | 正确路由 |
|---|---|
| Agent 身份、职责或稳定行为不清 | system 提示词候选，Role 主责 |
| 任务目标、输入、范围或验收不清 | task/user 提示词候选，Plan-PM 主责 |
| Lead 选择了错误 Agent | Lead 路由提示词或 Agent description 候选 |
| 项目接口、字段、UI 或架构事实错误 | 更新 `project/` 或接口契约，不改 system |
| 稳定技术知识不足 | Doc 判断知识候选；KB 不存动作规则 |
| 记忆或恢复上下文错误 | Memory 处理记忆候选或上下文选择 |
| 工具、MCP、Skills 使用错误 | 对应工具或能力文档，不用 Prompt 掩盖 |
| 权限、删除、锁、敏感内容问题 | Security 规则或确定性门禁，Prompt 只保留最小提醒 |
| 协作、广播、交接或执行顺序错误 | playbook、任务模板或工作区协议 |
| 模型能力与任务不匹配 | Lead 调整模型路由或任务拆分 |

如果证据不能证明提示词是根因，事件保持 E0 或路由给相应 Owner，不得创建“万能补丁”候选。

## 3. E0-E3

### E0：记录与观察

- 适用：单次、不可复现、证据不足或根因不属于提示词。
- 动作：写事件、关联任务和证据，记录观察窗口。
- 禁止：生成候选、修改 active、扩大权限。

### E1：生成候选

满足任一条件可进入 E1：

- 同类错误至少重复两次。
- QA 明确确认提示词缺陷。
- 用户明确纠正 Agent 的稳定行为。
- 输出契约稳定缺失。
- Lead 与对应 Owner 有证据确认 system 或 task/user 提示词是根因。

E1 只生成最小候选和失败转回归用例，不得覆盖 active。

### E2：低风险评测与受控激活

适用：

- 补充已有输出字段、读取顺序或验收步骤。
- 修正 Agent 路由关键词。
- 减少重复提示和 token。
- 澄清既有职责，不改变职责、权限或工具边界。

要求：

1. QA 完成静态、原始失败、既有基线和反向用例。
2. Role 或 Plan-PM 按提示词类型确认所有权和最小差异。
3. Security-Reviewer 确认无权限扩张、注入和敏感内容风险。
4. Lead 显式执行受控激活；“自动评测通过”不等于自动写入 active。

### E3：强制多方审批

以下变化必须进入 E3：

- Agent 核心职责、system 安全边界或 Lead 调度权。
- 工具、MCP、Skills、文件写入、删除、锁或敏感文件权限。
- Hooks、`settings.json`、模型或供应商。
- 允许访问新的数据范围或外部系统。
- 跨多个 Agent 的稳定行为和工程核心工作流。

E3 必须由 Role、QA、Security-Reviewer、Lead 全部给出批准结论；涉及不可逆、高成本、外部发布或用户权限时还需用户明确确认。

## 4. 状态生命周期

```text
observed -> candidate -> reviewing -> evaluated -> approved
         -> rejected
approved -> active -> monitored -> stable
                    -> rolled-back
```

- 每个状态变化必须关联事件、候选或评审文件。
- `shared/prompt-evolution/active-run.md` 只由 Lead 汇总。
- 多 Agent 并发时先追加各自文件，不直接抢写活动状态板。
- 修改活动状态板前按现有锁规则取得文件级锁。

## 5. Owner 与审批

| 阶段 | 主 Owner | 责任 |
|---|---|---|
| 信号采集 | 各 Agent / Hook | 只提交脱敏事实和证据 |
| 根因判断 | Lead + QA | 区分 Prompt 与非 Prompt 根因 |
| system 候选 | Role | 维护身份、职责和稳定行为 |
| task/user 候选 | Plan-PM | 维护目标、变量、范围和验收结构 |
| 回归评测 | QA | 创建失败转回归与反向用例 |
| 安全评审 | Security-Reviewer | 注入、权限、敏感内容、能力扩张 |
| 索引和图谱影响 | Doc | 检查链接和知识图谱，不把动作规则写入 KB |
| 受控激活与回滚 | Lead | 核验门禁、选择生效时间、监控和接管 |
| 恢复价值判断 | Memory | 只处理长期恢复候选，不保存单次流水 |

任何 Agent 不得单独完成“提出、评测、批准、激活”全链路。

## 6. 候选要求

候选必须包含：

- 来源事件、受影响 Agent、system/task 类型和目标文件。
- 当前版本、候选版本、内容哈希和上一版本。
- 最小差异及每一处差异对应的失败证据。
- 不改 Prompt 的替代方案及其排除理由。
- 风险等级 E1/E2/E3、Owner 和必要审批者。
- 原始失败用例、基线用例、反向用例和注入用例。
- token 变化、能力变化、权限变化和回滚目标。

不得把敏感内容、完整工具输出或未脱敏的用户数据放入候选。

## 7. 评测门禁

激活前至少证明：

1. 旧版本能复现或解释原始失败，新版本通过。
2. 既有基线没有不可接受退化。
3. 反向用例证明不会过度触发、误拒绝或误路由。
4. 输出契约、任务范围、工具和权限边界保持正确。
5. 注入与敏感内容检查通过。
6. 候选没有用堆叠冗余指令替代根因修复。
7. 新旧版本、评测环境和结果可追溯。

评测失败时回到 candidate 或 rejected，不得通过降低验收标准强行激活。

## 8. 受控激活

1. Lead 读取候选、评审、Owner 结论和回滚目标。
2. 确认所有目标文件未发生未纳入候选的漂移。
3. 创建激活前快照或可验证的上一版本引用。
4. 只应用候选声明的最小差异。
5. 更新版本、哈希、激活时间和活动状态。
6. 重新运行必要评测和结构校验。
7. 新版本从下一次 Agent 调用或新会话生效，不修改正在运行的 Agent。
8. 进入监控窗口；出现安全退化、原始失败复现或基线显著退化时立即回滚。

## 9. 回滚

- 回滚必须指向明确的上一 active 版本，不得凭记忆重写。
- 回滚不删除事件、候选或评审记录。
- 回滚后创建新的事件，说明触发原因、受影响任务和验证结果。
- E3 回滚由 Lead 与 Security-Reviewer共同确认；涉及用户权限时通知用户。
- 回滚完成后检查是否需要重新路由到工具、项目事实、工作流或模型。

## 10. KB、记忆与文档边界

- KB 不保存提示词动作规则、激活流程、事件、候选或评审。
- 单次错误不写入正式记忆；Memory 只筛选长期恢复价值。
- Doc 可以更新索引和图谱关系，但不得把本规则复制进 KB。
- 运行期事实以 `shared/prompt-evolution/` 为准，安全动作以本规则为准。

## 11. 禁止事项

- 失败后立即修改 active system 提示词。
- Hook 直接生成、评审、激活或回滚 Prompt。
- 让 Agent 自己批准自己的候选。
- 为通过评测而删除失败用例或降低验收标准。
- 在运行中的 Agent 上热替换 system 提示词。
- 用 Prompt 修补确定性权限、锁、删除或敏感文件门禁。
