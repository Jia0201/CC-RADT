# CC-RADT Secondary Development Guide

This guide is for maintainers who extend the CC-RADT harness itself. Use the root `README.md` when installing CC-RADT into a business project. Use this guide when changing agents, policies, hooks, Skills, MCP, prompts, memory, or packaging.

## 1. Branch Boundaries

| Branch or artifact | Purpose | Content |
|---|---|---|
| `main` | Stable runtime users can install | `.claude/`, `.mcp.json`, installation docs, and runtime files |
| `dev` | CC-RADT engineering source | Full agents, policies, tools, templates, lab, tests, and packaging pipeline |
| GitHub Release | Versioned user package | ZIP and checksum generated and verified by the packaging tool |

Never copy the `dev` tree directly to `main`. A stable runtime must be generated by `tools/bin/ai-teams-package.sh` so development logs, experiments, local state, secrets, and packaging tools do not leak into the user package.

## 2. Setup

Requirements: Git, Node.js 18+, Python 3, and either Bash on macOS/Linux or PowerShell 7 plus Git Bash/WSL on Windows. Claude Code is required to validate actual loading of project subagents, rules, settings, hooks, Skills, and MCP.

```bash
git clone https://github.com/Jia0201/CC-RADT.git
cd Claude-Code-Research-and-Development-Teams
git switch dev
bash tools/bin/ai-teams-check.sh
```

Read `CLAUDE.md`, `index/ENTRY.md`, `index/STATUS.md`, `playbook.md`, and `security/index.md` before editing. Then read the indexes for the capability being changed.

## 3. Directory Ownership

| Path | Primary owner | Purpose |
|---|---|---|
| `.claude/` | Role + Security-Reviewer | Official Claude Code adapters; not a second policy body |
| `agents/` | Role | Agent roles, workflows, memory, KB, Skills, MCP, and playbook pointers |
| `prompts/` | Role + assigned Agent | Versioned system, task, and retry prompts |
| `rule/` | Doc + Security-Reviewer | Low-token routing to authoritative content |
| `project/` | Doc | Managed project facts, architecture, APIs, UI, commands, status, and ADRs |
| `memory/` | Memory | Shared memory, per-agent memory, recovery, and compaction |
| `kb/` | Doc | Stable reusable knowledge, never live action rules |
| `shared/` | Plan-PM + record owner | Tasks, plans, locks, state, handoffs, broadcasts, supervision, escalation |
| `security/` | Security-Reviewer | Sensitive files, deletion, permissions, ownership, locks, state, and risk gates |
| `hooks/` | Security-Reviewer | Claude Code event automation and output contracts |
| `skills/`, `mcp/` | Role + Doc + Security-Reviewer | Portable capabilities, sources, licenses, and security boundaries |
| `tools/` | Command owner | Command docs, scripts, cross-platform wrappers, and verification tools |
| `templates/` | Doc + Role | Standard templates for agents, project files, rules, and hooks |
| `lab/` | Lead | Experimental capabilities excluded from runtime packages |

Check `security/file-ownership.md` and `security/lock-policy.md` before writing. Cross-owner changes require a handoff and review.

## 4. Standard Change Flow

1. Define the problem, goal, non-goals, impact, and acceptance criteria.
2. Read current project facts and related indexes; decide whether an ADR is required.
3. Create or update the task and execution plan in `shared/`; acquire locks for overlapping files.
4. Edit the single authoritative body and use links or short routing elsewhere.
5. Update affected indexes, agent pointers, knowledge graph relations, and status files.
6. Run focused tests, then the global checks.
7. Generate an isolated runtime package and validate it in a fresh directory.
8. Commit to `dev`; maintainers generate `main` and Release assets only after acceptance.

Use an ADR for durable changes to agent placement, core directories, command organization, memory layers, Hooks/MCP/Skills mechanisms, locks, indexing, retry, or prompt governance. The ADR entry is `project/adr/index.md`.

## 5. Extension Checklist

**Agent**: update `agents/<agent>/`, `.claude/agents/<agent>.md`, agent indexes, prompt assignments, memory, KB, Skills, MCP, graph links, and self-check assertions.

**Hook**: start from `templates/hooks/`, use a portable Node.js or shell entry, declare the event in settings, document it in `hooks/index.md`, validate the exact Claude Code JSON schema, and add a fixture. Resolve paths with `CLAUDE_PROJECT_DIR` or another portable runtime strategy.

**Command**: add documentation under `tools/commands/ai/`, implementation under `tools/bin/`, then update command and file indexes plus check counts. High-risk commands require a plan or dry run.

**Skill or MCP**: bundle a portable Skill copy with source, license, mode, and agent assignment. MCP configuration must use portable commands, URLs, or environment variables and must not contain credentials or absolute local paths.

**Prompt**: do not let a running agent edit an active prompt directly. Create a candidate, evaluate it, approve it, activate it, and keep rollback history under the prompt governance policies.

## 6. Validation

Run at least:

```bash
bash tools/bin/ai-teams-check.sh
bash tools/bin/ai-teams-e2e-fixtures.sh
node tools/bin/ai-teams-hook-output-test.mjs
node tools/bin/ai-teams-memory-audit.mjs --json
```

Use `bash -n <script>` for changed shell scripts and a structured parser for JSON. Initialization changes require isolated fixtures for projects without Git, frontend projects, backend projects, and projects with existing Claude configuration.

## 7. Build a Runtime

Use an empty output directory outside the repository:

```bash
bash tools/bin/ai-teams-package.sh formal \
  --version 1.1.0 \
  --install-layout claude-subdir \
  --output "$HOME/CC-RADT-dist/formal" \
  --verify
```

Verify that the package contains `.claude/ai-teams/`, `.claude/agents/`, `.claude/rules/`, `.claude/settings.json`, and root `.mcp.json`. It must not contain `lab/`, development logs, sessions, caches, private settings, secrets, packaging tools, absolute local paths, or live project/memory/workspace state.

## 8. Pull Requests and Issues

The authoritative branch, commit, version, package provenance, tag, release, and rollback rules are in `security/version-control-policy.md`. User-visible changes belong under `Unreleased` in `CHANGELOG.md` before release.

Keep each commit focused. A pull request must explain the problem, solution, affected boundaries, verification, risk, and rollback path. Structural changes require index/graph review by Doc, boundary review by Security-Reviewer, and behavior verification by QA.

Issue reports should include operating system, Claude Code and Node.js versions, branch and commit, command, expected and actual behavior, relevant Hook event, and a redacted minimal reproduction. Never attach credentials or sensitive business code.
