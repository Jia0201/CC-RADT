## 首版实施差异

- 内核、CLI 与本机网页已落入独立 Go 模块；网页使用无构建依赖的原生 JavaScript，平台层使用 Go 标准库与原生系统调用。
- 下载功能先由 CLI 提供，网页使用本地包；不假装提供尚未接入的在线版本选择器。
- 生成图谱与双方修改文本当前保守报冲突，没有自动重建和智能区块合并。显式迁移只实现数据文件改名，不执行包内脚本。
- 重启后输入项目重新预览，会优先发现未完成事务并提供恢复路径；恢复也可独立输入事务绝对路径。
- Windows 写入因 NTFS 元数据与持久化能力未验收而禁用；不能按下方目标矩阵宣称全平台已经可用。签名分发和实机断电验收尚待发布阶段完成。

## 1. 目标与边界

用户操作：退出目标项目的 Claude Code 和后台写入任务 → 打开独立升级器 → 选择项目与目标版本 → 查看变化并确认 → 完成后重启 Claude Code。

升级器在 Harness 之外运行，不调用 Lead、子 Agent、模型、旧版 Hooks 或旧版升级脚本。正式包通过外部工具安装；工程内升级指令后续只提供下载和操作说明。

核心要求是内容不丢失、不静默覆盖。升级前的安装与配置保留可恢复原件；新旧数据不混写。新增文件、弃用文件、本地自定义以及显式迁移均有记录。发生异常时先保护文件，不能以自动恢复为名覆盖新写入的数据。

不承诺多文件切换期间随时可运行，也不承诺硬件失效下绝对不丢失。可验证的保证是：在支持的平台和存储条件下，单次进程中断能被识别并独立恢复；未满足前提则阻止升级。原件留存不能替代异盘备份。

## 2. 技术选型

| 层 | 选择 | 目的 |
|---|---|---|
| 升级内核 | Go，选实施时受支持稳定版本并锁定补丁号 | 编译独立程序，不依赖用户安装 Node、Python、Git、rsync 或 Claude Code |
| 操作界面 | HTML/CSS/TypeScript，构建为静态资源，Go embed 内嵌 | 默认浏览器打开本机界面，与升级内核使用同一可执行文件 |
| 无桌面使用 | 同一 Go 内核的 CLI | Linux 服务器可使用 plan/apply/recover，无浏览器也能恢复 |
| 本机服务 | Go net/http，绑定 127.0.0.1 随机端口 | 仅本机访问；UI 与 CLI 不重复实现文件操作 |
| 包与清单 | ZIP、JSON、SHA-256、Ed25519 签名 | 明确版本、文件归属、来源与内容指纹 |
| 状态记录 | 每次事务独立目录，追加事件日志和校验清单 | 不引入数据库；可人工定位恢复材料 |
| 路径与锁 | Go filepath；golang.org/x/sys 平台适配 | Windows/Unix 分别实现锁、同步与元数据处理 |
| 测试 | Go 单元/集成测试、原生 OS CI、Playwright UI 测试 | 文件安全、故障恢复和交互分别验收 |

Go 支持 GOOS/GOARCH 构建目标，embed 可以在编译时嵌入静态资源：[Go 平台说明](https://go.dev/doc/install/source#environment)、[embed](https://pkg.go.dev/embed)。使用 CGO_ENABLED=0 为目标构建，仍必须在对应 OS 上运行测试。浏览器是 UI 的依赖；CLI 没有浏览器依赖。新 Harness 自身需要的 Node 等环境仍需单独检查，升级器独立不代表 Harness 无依赖。

第一期优先实现 Go 内核与 CLI，再接入简洁本机网页；不把维护完整桌面框架作为升级的前置条件。浏览器界面无法直接获取任意本机文件夹绝对路径，首版提供粘贴路径、路径校验和只读识别，不伪装浏览器文件选择为原生目录选择器。

## 3. 平台适配与交付

| 平台 | 架构目标 | 首期存储验证 | 交付 |
|---|---|---|---|
| Windows 11 | amd64、arm64 | 本地 NTFS | ZIP 内独立 exe；签名与原生运行测试由发布链路提供 |
| macOS | Apple Silicon、Intel | 本地 APFS | 对应架构二进制及轻量启动入口；公开分发需签名/公证验证 |
| Linux | amd64、arm64 | 本地 ext4 | 二进制；CLI 和可选本机网页 |

支持操作系统最低版本以锁定 Go 工具链和 CI 实测结果为准，不仅凭成功编译宣布支持。没有原生测试证据的架构标记未验收。默认普通用户权限，不要求管理员或 sudo；权限不够即停止。

第一期不在网络共享、云盘同步目录、跨卷事务目录上执行升级。不能确认存储条件时要求用户处理后重试。覆盖中文、空格、大小写冲突、Unicode 规范化、Windows 保留名、长路径和文件占用。包内拒绝绝对路径、越界路径、符号链接、junction/reparse point、大小写碰撞、重复条目及解压体积超限；已有安装遇到无法保真的链接、ACL 或特殊文件则停止，不展开或丢弃。元数据保留能力要按平台验收。

## 4. 用户原型流程

1. 选择项目：粘贴项目路径；显示识别到的 Harness 路径、产品版本、构建身份。
2. 选择包：Release 在线列表或本地正式包。显示目标版本与可用迁移路线。
3. 升级预览：新增/更新/停用/保留数量；配置合并摘要；备份位置；环境和会话条件。
4. 冲突：逐项展示路径、双方变更原因；允许导出报告、重新扫描或取消。不提供“强制覆盖全部”。首版不自动合并双方都改过的 Markdown。
5. 执行：保护旧安装 → 构建新副本 → 应用迁移 → 检查候选 → 切换 → 完成。
6. 中断恢复：下一次打开自动显示未完成事务，先恢复一致安装；不允许启动第二次升级。
7. 完成：展示版本、项目数据保护结果、备份与报告位置，提示重启 Claude Code。

UI 显示后台实际状态，不能靠计时器推断完成；本方案附带的原型计时器仅为模拟。切换前可取消；切换开始后按钮改为“安全停止并恢复”，不得随意终止一半操作。用户强杀进程时，下一次启动从事务记录恢复。

## 5. 文件分类：混合目录按文件处理

| 类别 | 例子 | 策略 |
|---|---|---|
| 官方系统 | Hook、工具、安全规则、官方 Agent 定义 | 用旧基线/当前/新版三方比较更新 |
| 项目数据 | project 画像、需求、记忆条目、任务与会话记录 | 保留字节；声明格式迁移时只在副本中转换 |
| 本地扩展 | 自装 Skills/MCP、rule/custom、用户 Agent | 不替换、不停用；同名冲突阻断 |
| 生成材料 | 动态索引、图谱、运行清单 | 在副本中重建受管区块，保留人工内容与自定义关联 |
| 混合配置 | settings.json、.mcp.json、注册表 | 按键及来源标识做三方合并 |

memory、kb、project、shared、prompts 同时包含系统文档与数据，不能只按目录排除或覆盖。提示词演进后的激活版本和编译 Agent 属于项目定制，不能直接被官方默认值替换；新版运行器若不兼容旧定制，明确冲突，不把“保留文件”误当“功能仍有效”。

没有出现在可信旧清单中的文件视为未知/本地文件。新版不再包含的旧文件，仅在确认官方归属、字节未改且无依赖后退出活动目录，原件保留在事务备份；本地删除的官方文件也作为本地变更识别，不默认恢复。

## 6. 正式包契约

每个包新增升级元数据，并与运行内容一同签名：

```text
formal-v1.1.0/
  .claude/                       # 安装内容
  .mcp.json                      # 如该包布局提供
  upgrade-manifest.json
  migrations/                    # 声明式步骤
  baselines/                     # 支持旧构建的官方文件基线或可信摘要
  checksums.txt
  package-signature.json
```

升级器二进制作为独立附件，放在目标 Harness 之外运行，不放进 .claude/ai-teams 的执行链。迁移目录和基线是分发元数据，不复制为 Claude Code 的工作文档。

清单字段：product、version、buildId、sourceCommit、layoutVersion、dataSchemaVersion、minimumUpdaterVersion、supportedSourceBuilds、files、migrations。files 每项含 path、hash、ownerClass、mergePolicy；改名包含显式 from/to。构建身份由签名清单覆盖的 payload 文件集生成，不能将 buildId 自身放进自己的哈希输入。

每次打包自动生成新增/更新/停用差异，开发者仅补文件分类调整、显式改名和数据迁移规则。默认动作是拒绝未知操作；包不得提供任意 shell、PowerShell 或下载执行命令。复杂迁移用经过测试的升级器内置迁移器 ID，包只声明参数，必要时提高最低升级器版本。

## 7. 跨版本和旧版首次接入

产品版本、数据格式版本、升级器版本分别管理。产品新增功能但数据格式未变时可直接更新；跨格式按迁移图选择经过验证的完整路径。目标包携带支持路径全部步骤，或在升级前下载并核验完全部依赖，切换阶段不依赖网络。

当前仓库曾多次用 1.0.0 生成不同内容，因此 VERSION=1.0.0 不足以确定旧基线。旧版适配以官方清单、受管文件摘要、可信历史包映射识别具体构建。不能仅靠版本字符串、当前已修改文件或新生成的清单自证原始身份。无法确定时允许只读预览，禁止自动 apply。

首期只支持已确认具体旧构建的 1.0.0 → 1.1.0。1.x → 2.x 在原型中是规划场景，必须有真实 v2 清单、迁移和证据后才能启用。支持版本矩阵随正式包发布，不能声称任意旧版可直升最新版。

已经公开的版本包、标签与校验值不得回写来补升级清单。对已有 1.0.0/1.1.0 包，用独立签名的兼容描述绑定其原始 payload 摘要；升级器验证描述和原包后处理。未来正式包直接内置新契约；需要修正运行内容时发布新补丁版本，由发布 Agent 交付。

## 8. 三方合并与配置保护

- 当前等于旧基线：应用新版；当前等于新版：无需动作。
- 新版等于旧基线、当前不同：保留当前；本地删除同样计为修改。
- 双方不同：JSON 只合并互不冲突且有明确归属的键；文本首版阻断并导出差异，不执行语义猜测。
- 本地新增与新版新增同路径：相同字节可认领，不同字节阻断。
- 未知字段、重复 JSON 键、语法不合法、无法解析的配置：不丢弃字段，阻断修改该配置。

settings.json 中仅操作基线确认属于 CC-RADT 的配置；Hook 以事件/匹配器/执行器身份识别，列表不能整体覆盖或重复追加。permissions 不擅自扩大，官方新增权限在预览中列明。settings.local.json 原样保留，不被模板重建；如果其优先级导致新配置无法生效，报告冲突。[Claude Code 设置说明](https://code.claude.com/docs/en/settings)

CLAUDE.md 只合并明确受管区块；没有边界且双方修改则阻断。.mcp.json 保留本地服务和参数，未知插件、Agent、Rules 均保留。敏感值只在本机必要的配置合并或字节级备份中流转，报告与网页仅显示字段路径和脱敏摘要，不上传模型/遥测；不解析 .env、私钥或证书内容。

## 9. 事务和失败恢复

事务目录默认位于项目所在卷的外部同级位置，例如：

```text
workspace/
  target-project/
    .claude/ai-teams/
  .cc-radt-upgrades/
    <project-id>/<transaction-id>/
      original/                  # 只增不改的恢复原件
      candidate/                 # 新版及合并结果
      journal/                   # 切换步骤及哈希
      reports/                   # 不含敏感正文
```

project-id 使用规范化真实路径标识，事务目录限制当前用户访问。只备份 Harness 和将变更的外层受管文件，不把整个业务仓库搬入备份。禁止把事务放入会被替换的目录或递归备份自己。当前安装的保留文件仍可能含隐私，原件目录不得公开提交。

执行步骤：

1. 读取清单和版本，验证签名、内容哈希、路径、空间和兼容路线，生成只读计划。
2. 要求关闭目标项目所有 CC 会话、Agent、观察器/Hook 写入及编辑任务；不自动强杀进程。取得项目升级器独占锁。
3. 锁只防另一个升级器；它无法阻止旧 Claude 或任意编辑器。核对进程/安装现有活动证据，备份期间与切换前比较文件集和哈希。有变动即停止重做计划。旧版缺少协作租约，需人工维护窗口；无法确认停止写入时不执行。不存在凭“静默几秒”证明永不再写入的保证。
4. 用独立文件副本备份受管安装和待变更配置；保留必要元数据并核对清单/哈希。不得使用与原件共享可写内容的硬链接。
5. 在 candidate 中构建新安装、保留数据、运行迁移和合并；校验数据守恒、引用、配置和运行兼容性。默认不执行新包提供的任意脚本。
6. 切换前写持久事务意图；每个文件/目录操作写完成记录及前后哈希。外部配置和 ai-teams 目录属于同一事务，不能只恢复其中一部分。VERSION 最后写入，完成标记晚于所有检查。
7. 切换时将旧活动对象移动到留存路径后放置候选；按平台实现可靠文件落盘、目录元数据处理与占用失败分支。跨文件变更不宣称整体原子；中途失败或进程中断进入 RECOVERY_REQUIRED，禁止再运行 Harness，外部工具恢复后才解锁。
8. 恢复根据日志及磁盘实际哈希确认已完成步骤，不只相信日志最后一行。恢复动作本身可中断、可重复；回写前若检测到升级后新增/修改内容，先另行保留并停止自动覆盖。
9. 完成后保留旧安装、迁移前数据和报告，不自动清理备份。用户另行决定清理；取消产生的候选目录也不得误清理原件。

Go 官方明确说明非 Unix 平台 Rename 即使同目录也不保证原子，因此文件系统适配不能用一个通用 rename 代替事务：[os.Rename](https://pkg.go.dev/os#Rename)。进程中断恢复和实际断电持久性分别测试；平台无法满足必要落盘能力时缩小支持范围。

“刚升级失败恢复”恢复完整旧状态；“新版已使用数日后降级”需保护新增数据、检查旧版可读性。首版只提供事务恢复，不提供会用老快照抹掉新数据的一键历史降级。

## 10. 外部界面与来源安全

在线默认 GitHub Release 的正式附件，不执行 main/dev git pull。固定仓库白名单、明确版本、拒绝隐式降级和版本标签复用；支持相同版本不同 buildId 的识别与阻断。离线本地包使用相同验证流程。

SHA-256 只证明内容一致，不能单独证明可信来源。升级器固定可信发布公钥，验证 Ed25519 签名清单及 payload；密钥轮换须由已信任密钥授权或可信新版安装器更新。发布方可另外启用 GitHub immutable releases 和 attestation：[GitHub 官方说明](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)。旧版无签名只允许使用经发布方明确登记的可信旧基线，不能静默降级校验。

网页仅服务嵌入资源，无 CDN、分析脚本、远程字体或业务数据上传。每次启动随机鉴权值、严格 Host/Origin 校验、CSRF 防护和 CSP。修改请求仅 POST，需有效计划 ID 和匹配的项目哈希；恢复也是显式操作。只读 GET 不触发扫描外任意写操作。访问凭据不进查询日志，UI/报告不显示密钥和业务正文；关闭网页不代表关闭事务，CLI 可继续查询或恢复。

## 11. 实施任务与交付门

以下是开发顺序，不是对完成时间的保证。各阶段验收后再进入下一阶段。

| 阶段 | 任务 | 交付 | 验收门 |
|---|---|---|---|
| P0 契约 | 盘点旧包真实 build；逐文件分清系统/数据/定制；确定配置归属 | 清单 Schema、1.0.0 基线、支持矩阵、ADR 草案 | 无来源不明文件被自动认领 |
| P1 只读规划 | Go 项目、包验证、路径校验、三方比较、JSON 合并计划 | CLI plan + JSON/文本报告 | 对原安装零写入；混合目录/冲突/未知构建用例通过 |
| P2 保全与事务 | 平台锁、空间评估、元数据备份、暂存、日志、恢复 | apply/recover 内核 | 每个写入边界故障注入后原件完整；恢复可重复 |
| P3 升级路径 | 旧版适配、迁移路由、索引重建、配置合并 | 1.0.0 → 1.1.0 正式迁移定义 | 长期使用 fixture 数据守恒；缺迁移边拒绝 |
| P4 用户入口 | 嵌入网页、真实状态接口、CLI 同步、冲突与恢复页 | 本原型对应的可用界面 | UI 不伪报完成；取消/断连/恢复行为一致 |
| P5 发布交接 | 包装升级清单、签名接口、六架构构建、原生测试 | 独立程序、正式包、测试证据、升级说明 | 每个声明支持的平台和来源版本都有证据 |

主工程拟新增独立 Go 模块 updater/，包含 cmd/cc-radt-updater、internal/{manifest,baseline,planner,merge,migration,transaction,platform,server}、web、fixtures。不放在 hooks 内，也不依赖 ai-teams-lib.sh。

主工程拟修改：tools/bin/ai-teams-package.sh 生成包清单与迁移元数据；tools/commands/ai/upgrade-existing.md 改为外部升级说明；tools/bin/ai-teams-upgrade.sh 的危险 apply 停用并提示外部工具；补充 security/upgrade-policy.md、ADR 和索引。是否沿用/移除旧脚本由兼容方案决定，不在本设计阶段修改。

职责：本 Agent 负责主工程接入、升级内核和正式打包；专门 UI Agent 可按原型实现升级器页面；观察台 Agent 仅提供其数据位置与版本兼容契约；发布 Agent 负责签名凭据、main/标签、GitHub Release 和平台分发。升级工具与现有观察台保持独立进程与独立写入权限。

## 12. 测试矩阵与稳定性证据

- 长期使用 fixture：项目画像、多个任务与记忆、压缩/归档、提示词演进、自装 Skills/MCP、用户配置和人工索引；未迁移文件字节哈希一致，迁移对象有完整字段/记录映射。
- 文件变化：新增/更新/停用/改名、本地删除、同名不同内容、同版本不同 build、未知旧基线、重复运行、迁移失败。
- 平台故障：只读权限、文件占用、磁盘满、备份空间不足、中文/空格路径、大小写冲突、链接与越界 ZIP、两升级器竞争、写入者活动。
- 故障注入：每个变更原件的动作之前/之后、事务记录落盘之前/之后终止进程；恢复中再次中断。另在可控 VM 验证断电场景，不能拿普通异常代替断电测试。
- 跨版本：每个公开支持路径都由保留 fixture 回归；未发布 v2 用模拟 Schema 测迁移引擎，不将其记为真实 v2 支持。
- 真实 CC：隔离项目加载官方 Agent、Rules、Hooks、MCP 配置；读取历史项目资料和记忆并完成小任务。运行测试不调用真实业务项目的部署或危险命令。
- 首版公开支持须通过相应 OS 原生测试；仅编译成功不算通过。Windows/macOS/Linux 各自输出结果和限制，恢复功能在无 CC/无网络环境可运行。

发布阻断项：任何数据丢失、静默覆盖、无法恢复、元数据丢弃、半安装误报成功。用户端只运行必要完整性/兼容性/备份检查；全面破坏性测试在开发和打包阶段的隔离环境进行。
